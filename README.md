# FloodLens AI

Satellite-powered flood damage and accessibility intelligence.

> **AI connects satellite evidence to human impact.**

## Multimodal AI Hackathon 2026 — Track B

**Mapping Flood Damage from Space**

FloodLens turns Sentinel-1 SAR observations into an actionable disaster map:

**Satellite evidence → candidate flood/change detection → infrastructure impact → road-network accessibility → potentially isolated communities → evidence brief**

The system is designed to keep the detection layer transparent and use Gemini as an explanation/reasoning layer rather than treating an LLM as the flood detector.

## Live demo

**Production:** https://floodlens-ai.vercel.app

The current demo uses a real **Lokoja, Kogi State, Nigeria — 2022 flood event** dataset generated by GitHub Actions from Copernicus Data Space Sentinel-1 imagery and OpenStreetMap.

## Current real-data result

- **Before:** Sentinel-1A — 2022-09-19
- **After:** Sentinel-1A — 2022-10-13
- **Observation gap:** 24 days
- **Candidate flood/change extent:** 10.11 km² after spatial cleanup
- **Raw candidate pixels:** 14.72%
- **Cleaned candidate pixels:** 9.21%
- **Potentially affected road segments:** 60
- **Potentially affected bridges:** 2
- **Mapped communities:** 4
- **Potentially isolated communities:** 1

> These are analytical indicators, not claims of confirmed structural damage or confirmed physical isolation. Sentinel-1 backscatter change can have multiple causes, and OpenStreetMap coverage is not guaranteed to be complete.

## Architecture

- **Frontend:** Next.js App Router + TypeScript + Tailwind
- **Map:** MapLibre GL
- **Backend:** FastAPI/Python
- **Geospatial:** GeoPandas, Shapely, Rasterio, NetworkX
- **AI:** Gemini for evidence explanation/reasoning
- **Satellite:** Sentinel-1 GRD via Copernicus Data Space
- **Infrastructure:** OpenStreetMap
- **CI/CD:** GitHub Actions + Vercel

## Analysis method

1. Search Copernicus Data Space for compatible Sentinel-1 scenes.
2. Select a before/after pair from the same Sentinel-1A relative orbit and acquisition mode.
3. Process VV and VH backscatter through the Sentinel Hub Processing API.
4. Flag pixels showing a configurable decrease in both polarizations.
5. Remove small connected components to reduce isolated speckle/noise.
6. Overlay the candidate change area with OSM roads and bridges.
7. Build the road graph from the **full OSM node sequence of each road way**, preserving intersections.
8. Remove potentially affected road segments and test whether mapped communities still have a route to configured AOI boundary exits.
9. Generate a cautious evidence brief from the measured results.

## Reproducibility

The live analysis is automated in:

`.github/workflows/floodlens-live.yml`

The workflow:

- installs the geospatial Python stack,
- runs the test suite,
- authenticates to Copernicus using GitHub Actions secrets,
- retrieves real Sentinel-1 observations,
- runs the Lokoja analysis,
- writes GeoJSON/GeoTIFF/JSON outputs,
- commits the web-ready dataset back to `main`,
- uploads the complete analysis as a workflow artifact.

The web build is independently checked with:

`.github/workflows/floodlens-web.yml`

## MVP principle

The demo can fall back to a deterministic event dataset if live satellite retrieval is unavailable. Live retrieval is an enhancement to the reproducible demo, not a single point of failure.

## Safety and uncertainty

FloodLens deliberately uses terms such as **candidate flood/change**, **potentially affected**, and **potentially isolated**.

Satellite imagery alone cannot establish that a building, bridge, or road is structurally destroyed. Likewise, a graph-based accessibility result indicates that no mapped route remains under the configured assumptions; it does not prove that residents are physically trapped.
